# copilot/ — Offline LLM Copilot (Phase 4)

Standalone FastAPI service (`:8400`) that turns a Phase 3 RCA incident into an
**operator-readable root-cause narrative** — Summary / Likely root cause / Blast
radius / Recommended checks — grounded in local runbooks and generated by a
**local Ollama LLM**. Fully offline: zero outbound calls, no model downloads at
runtime.

This is the "so what do I do about it" layer on top of the rest of the stack:

- **Phase 2 (`ml/`, `:8200`)** — what/when: precursor probability + time-to-impact.
- **Phase 3 (`rca/`, `:8300`)** — where: correlated incident, root cause, cascade.
- **Phase 4 (this service, `:8400`)** — why + what to do: a grounded narrative.

See the full design: [`docs/superpowers/specs/2026-07-14-phase4-offline-copilot-design.md`](../docs/superpowers/specs/2026-07-14-phase4-offline-copilot-design.md).

## How it works

1. `rag.py` — a pure-Python **TF-IDF retriever** over `data/runbooks/*.md` pulls the
   runbook sections most relevant to the incident. No embeddings, no vector DB, no
   network (see "Retrieval" below).
2. `prompt.py` — renders the incident (root cause, symptoms, cascade) plus the
   retrieved runbook excerpts into strict system+user chat messages.
3. `llm.py` — a thin, **model-agnostic** Ollama `/api/chat` client (low temperature,
   thinking suppressed). Any failure degrades gracefully rather than raising.
4. `explain.py` — orchestrates retrieve → prompt → generate, with a deterministic
   **templated fallback** (built from the RCA facts + runbook headings) when the LLM
   is unavailable.

## Prerequisites

A local [Ollama](https://ollama.com) server running on `http://localhost:11434`
with a chat-capable model pulled. The model is selected by `COPILOT_MODEL`
(default `mistral:7b`, the roadmap target). It is **model-agnostic** — point it at
whatever you have pulled, e.g.:

```bash
COPILOT_MODEL=qwen3:8b python -m copilot.main
```

## Running it

Requires Python 3.11+. From the **repo root**:

```bash
pip install -r copilot/requirements.txt
python -m copilot.main            # listens on :8400
```

Explain an incident — either POST the full incident, or just its id (the service
fetches it from the rca service at `COPILOT_RCA_URL`):

```bash
# by id (requires rca :8300 running)
curl -s -X POST localhost:8400/explain -H "Content-Type: application/json" \
  -d '{"incident_id": "inc-74cedb75"}' | python -m json.tool

# or with the full incident payload (no rca dependency)
curl -s -X POST localhost:8400/explain -H "Content-Type: application/json" \
  -d '{"incident": { ...incident dict from :8300/incidents... }}'
```

## API (`:8400`)

| Endpoint | Description |
|---|---|
| `POST /explain` | Body `{"incident_id": "..."}` (fetched from rca) or `{"incident": {...}}` (full dict). Returns `{incident_id, root_cause_node, model, llm_available, narrative, retrieved_runbooks}` |
| `GET /health` | Liveness |

If Ollama is unreachable, `/explain` still returns **HTTP 200** with
`llm_available: false` and a templated narrative built from the RCA facts — the
operator always gets the localized root cause + runbook pointers.

## Retrieval (why lexical, not vector RAG)

The roadmap named ChromaDB, but its default embedder downloads from HuggingFace on
first use, which breaks the hard offline constraint; and the local Ollama server in
the reference environment has its embedding endpoints disabled. So retrieval is a
deterministic pure-Python TF-IDF cosine ranker — ample for a small, scenario-keyed
runbook corpus. An embedding retriever (Ollama `/api/embed` started with
`--embeddings`, or ChromaDB with a pre-baked local embedder) can be dropped in
behind the same `Retriever` interface later for semantic recall on a larger corpus.
